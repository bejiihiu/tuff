# Scheduler evidence stand

This directory documents the benchmark and soak harness that produces the evidence for region scheduler
changes. It exists because a scheduler claim needs numbers that can be reproduced, audited and rejected:
one built server jar, fixed load, randomized arm order, guardrails that invalidate a run, and statistics
computed from the artifacts rather than from a summary someone typed.

The stand is not part of the server or of CI's default build. It lives in `tuff-benchmarks/src/main/java`
and uses the JDK only: no external dependency, no mock, no hand written result file.

## What it compares

| Arm | Configuration | Purpose |
| --- | --- | --- |
| `A` | `threaded-regions.scheduler: EDF` | baseline |
| `A2` | the same EDF configuration, measured again | A/A calibration of the stand's noise |
| `B` | `KAIROS` with `kairos.elastic: false` | the EDF port with a fixed fund |
| `C` | `KAIROS` with `kairos.elastic: true` and a ceiling above the floor | elasticity |

Arms differ by one factor each: `A` to `B` changes the scheduler class, `B` to `C` turns growth on.
`A2` exists only to prove how much of a difference the same configuration can produce by itself.

Load profiles, all produced by real console commands on a real server:

| Profile | What it does |
| --- | --- |
| `steady` | fixed force-loaded areas and a fixed entity count |
| `churn` | areas are dropped and re-added, a slice of entities is replaced |
| `burst` | entity spikes followed by troughs |
| `idle-compute` | few regions, no entity work; the compute lane stays unloaded |

## Quick start

```bash
# build the server jar first
./gradlew :tuff-server:createPaperclipJar
./gradlew :tuff-benchmarks:jar

JAVA=<jdk-25>/bin/java
JAR=tuff-server/build/libs/tuff-paperclip-26.3.local-SNAPSHOT.jar
CP=tuff-benchmarks/build/libs/tuff-benchmarks-26.3.local-SNAPSHOT.jar

# a smoke run: proves the stand works, proves nothing about performance
$JAVA -cp $CP kz.bejiihiu.tuff.bench.TuffBench run \
  --jar $JAR --profile steady --measure 60 --warmup 20 --sample 5000 --areas 2 --entities 60

# a block: ten runs per arm, randomized inside each block, then the analysis
$JAVA -cp $CP kz.bejiihiu.tuff.bench.TuffBench suite \
  --jar $JAR --blocks 10 --warmup 600 --measure 1800 --areas 4 --entities 600

# recompute the report from the stored summaries
$JAVA -cp $CP kz.bejiihiu.tuff.bench.TuffBench analyze --dir run/bench/<bench-id>

# check the analyzer's pure parts without starting a server
$JAVA -cp $CP kz.bejiihiu.tuff.bench.TuffBench self-check
```

Artifacts go to `run/bench/<bench-id>/`, which is already outside version control. One block directory
contains `plan.json` (written before the first run), `env.json`, one directory per run, and the analysis.

## Artifacts per run

```text
runs/<arm>-<profile>-<nn>/
  manifest.json            git head, dirty state, patch hashes, jar hash, JDK, JVM flags, host, config hashes, windows
  server.log               captured console output
  gc.log                   -Xlog:gc* with time, uptime, level and tags
  jfr/recording.jfr        JFR profile recording, dumped on exit
  ticks.csv                per sample region aggregate: TPS, MSPT, lag share, entities, chunks
  fund.csv                 per sample fund counters (Kairos only; EDF rows carry -1)
  snapshots/               raw console blocks of the first, last and every tenth sample
  os/threads-*.txt         thread dumps taken by jcmd during the run
  summary.json             the run reduced to the numbers the analyzer compares
  analysis.md              the run report, generated by the tool
```

One block directory additionally contains `summary.csv`, `compare.csv`, `summary.json` and `analysis.md`.

## What the numbers mean

`hard miss` is the primary metric. In the running server no per-tick `scheduledStart`,
`tickStart` or `periodsAhead` is exposed, so a sample counts as a hard miss when the real region
aggregate shows either a lost period or a full-period tick:

```text
hard miss (per 5 s sample) := min region TPS < 19.5  or  worst tick of the window >= 50 ms
```

The summary names this source as `sampled_region_aggregate_proxy` and the report repeats it. Exact
per-tick ingestion is deliberately not faked; see [harness.md](harness.md) for the full list of what the
stand does and does not observe.

Secondary metrics are the distribution of the per-sample average and peak MSPT, the lowest region TPS,
the lagging region share, fund size and churn, thread seconds, JVM CPU and GC facts read from the JFR
recording. The analyzer treats a run as one observation: bootstrap intervals are built over runs, never
over ticks.

## Validity

A run is invalid when any of these holds:

- the process did not exit with `0`;
- the log contains a watchdog dump, an asynchronous-catcher violation, a failed region tick, an
  uncaught or unexpected exception, or an out-of-memory error;
- fewer than two measurement samples arrived or the window is shorter than 95% of the requested one;
- no region was ticking;
- the JFR recording is missing or unreadable.

Invalid runs stay on disk with their reasons and their guardrail evidence; they are excluded from the
statistics and listed in the report. The harness exit code is `3` when at least one invalid run exists,
so a CI job cannot mistake "ran" for "trustworthy".
